# DS-buddy 是怎么想的：从多 agent 到上下文
> 短文只讲了结论。这一篇把依据摆出来：各家产品选了什么抽象，上下文在 agent 之间到底是怎么传的，DS-buddy 里每一条是怎么落的。

Hi 大家。这是[那篇短文](../)的长文版，思路一样，多了对比和截图。

## 最前面的问题：人在当胶水

agent 越来越能干，用它的人却越来越忙。忙的都是搬运：复制一段群聊，贴一个文件，把这个对话里的结论贴给那个对话，给新开的 agent 再讲一遍昨天做到哪。多 agent 的产品又加了一份：给 agent 起名字，配技能，盯着一屋子对话看谁卡住了。一天下来，人大部分时间在当胶水。真正该人做的事，想清楚方向、做出判断，反而没时间做。

这件事有人量过：

- 2022 年《哈佛商业评论》上的[一项研究](https://hbr.org/2022/08/how-much-time-and-energy-do-we-waste-toggling-between-applications)跟了 20 个团队。按当时的报道，一个人一天在应用和网页之间切换约 1,200 次，每周花在切换之后重新进入状态上的时间将近 4 个小时，约占全年工作时间的 9%。
- 加州大学尔湾分校的 Gloria Mark 观察过被打断的工作。她在[一次访谈](https://news.gallup.com/businessjournal/23146/too-many-interruptions-work.aspx)里给的数字是：被打断的事，平均过 23 分 15 秒才接着做。
- 2026 年 3 月，BCG 在《哈佛商业评论》上发了一份对 1,488 名美国职场人的[调查](https://hbr.org/2026/03/when-using-ai-leads-to-brain-fry)，把用 AI、盯 AI 超出承受量带来的疲劳叫作 AI brain fry。按 [The Decoder 的报道](https://the-decoder.com/study-warns-of-ai-brain-fry-as-workers-hit-cognitive-limits-overseeing-ai-agents/)，要一直盯着 AI 干活的人，脑力消耗多 14%，信息过载多 19%；同时用的 AI 工具到三个，自己感觉到的效率见顶，再多反而往下掉。数据都是受访者自己报的。

前两个数字说的是 AI 之前的事。第三个说的是现在：工具换成了 agent，搬运和盯着的活没有少。

所以做 AI 应用产品，我觉得排在最前面的问题只有一个：降低人和 AI 沟通时要占的带宽。人说得越少越好，AI 还得把事办对。

我希望人只做五件事：说目标，指给它看，标注对错，舒服地观测，再把重复的摩擦降下来。下面每一个设计，都是在删掉这五件事以外的沟通。

## 为什么各家都先走向了 agent

因为我们习惯了通过人来组织上下文，习惯了各司其职。所以这一年的产品，摆到你面前的多半是「人」。

| 产品 | 摆在你面前的抽象 | 你要管的 |
| --- | --- | --- |
| Raft、Multica、Claude Code Agent Teams | agent 是队友：有名字、身份、记忆和自己的收件箱 | 起名、配技能、看谁卡住了 |
| Manus Cue | 每个 agent 有自己的邮箱、电话和钱包 | 一支要带的团队 |
| Claude Code、Kimi Code、Codex | 一个主 agent，加一次性的子 agent | 把任务说全，等它汇总 |
| Manus Wide Research、Kimi Agent Swarm | 一个总指挥，加几百个分身 | 一次一个问题 |
| Genspark、Cursor 2.0 | 同一件事，几个模型各做一遍 | 挑模型，挑结果 |
| OpenClaw、OpenHuman、ChatGPT Pulse | 一个一直在的助理 | 一段越来越长的对话 |
| dsh-superagent | 工单和一块面板，会话完全藏起来 | 只看面板 |

但对 AI 来说，干活需要的只有两样东西：上下文和模型。一个 agent 拆开看，就是一部分上下文加一个模型。我自己的代码里也是这样：一个「助理」只有三样东西，名字、一段人设、默认用哪个模型，会话是按任务开的。

人和人差别很大，所以才要分岗位。agent 和 agent 之间的差别极小：同一个模型换一段人设，「设计师」就成了「工程师」。真正有差别的是背后的模型。

再想一步：同一个项目里开三个对话，和拉三个 agent 围着同一件事干活，区别在哪？我想了很久，觉得没有区别，都是三份上下文，后面各接一个模型。对话（session）只是 agent 那一侧装上下文的办法，一条线，只往后加。人想事情不按对话想，一件任务也不该被一条对话框住。

所以我的看法是：**管理 agent，就是管理 context。**把上下文再包装成一个有名字的角色，是多出来的一层抽象。下面按五种组织方式，看各家是怎么做的。

### 角色团队

代表：[Multica](https://github.com/multica-ai/multica)、[Raft](https://raft.build/zh-cn/resources/blog/introducing-raft-where-humans-and-agents-build-together/)、[Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams)、[DS Bot](https://github.com/Fei2411/DS-Bot)、[Manus Cue](https://manus.im/blog/introducing-manus-2-0)。

{{fig:roles|角色团队：每个 agent 一份自己的上下文，靠互相发消息对齐。}}

做法：Multica 把 agent 当成队友，有个人档案，在看板上领 issue、报阻塞，还能编成小队。Raft 说得最直接，agent 是一等公民，有记忆、有身份、有自己的收件箱，在频道里 @ 队友、认领任务。Claude Code 的 Agent Teams 里每个队友是一个独立实例，靠磁盘上的共享任务清单和互发消息来协调。Manus Cue 给每个 agent 配了自己的邮箱、电话和钱包。DS Bot 和 DS-buddy 一样建在 DeepSeek Harness 上，有一个总管 bot，bot 之间可以 @ 接力。

观点：这一派最直观，代价落在人身上。组织单位是 agent 和对话，谁在做什么、谁卡住了、一件事做到哪了，要去对应的对话里翻。agent 越像人，你就越像一个经理。

### 总指挥加分身

代表：[Anthropic 的研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)、[Manus Wide Research](https://manus.im/blog/manus-wide-research-solve-context-problem)、[Kimi Agent Swarm](https://www.kimi.com/help/agent/agent-swarm)，以及 Codex 和 Claude Code 的子代理。

{{fig:orchestrator|总指挥加分身：每个分身拿一份干净的上下文，互相不说话，只把结论交回去。}}

做法：Anthropic 的研究系统用一个主 agent 带一群并行的子 agent，内部评测比单 agent 好 90.2%，代价是 token 用量大约是普通聊天的 15 倍。Manus 的 Wide Research 一次派出几百个分身，每个拿一份全新的上下文；它自己也写明，不适合前后步骤强依赖的任务。Kimi 的 Agent Swarm 专门训练了总指挥，最多调度 300 个子 agent。

观点：我觉得这一派是对的。它解决的是同时处理很多条互不相干的东西，比如调研一百家公司。前后有依赖、要做好几天的事，它帮不上太多，做完之后也什么都不记得。

### 并行比稿

代表：Genspark、[Cursor 2.0](https://cursor.com/blog/2-0)。

{{fig:parallel|并行比稿：同一个任务交给几个模型，起作用的单位是模型。}}

做法：Genspark 把同一件事交给多个模型，再由聚合器汇总。Cursor 2.0 让多个 agent 各在自己的工作副本里并行，同一个任务可以让几个模型各做一遍，你挑最好的。

观点：到这一步，已经没人关心 agent 叫什么了。你关心的只是用了哪个模型、结果靠不靠谱。这其实已经在说明，角色那一层可以拿掉。

### 常驻助理

代表：[OpenClaw](https://github.com/openclaw/openclaw)、[OpenHuman](https://github.com/tinyhumansai/openhuman)、[ChatGPT Pulse](https://www.bloomberg.com/news/articles/2025-09-25/chatgpt-feature-offers-users-a-personalized-daily-briefing)。

{{fig:assistant|常驻助理：上下文自己进来了，但所有事都挤在一段对话里。}}

做法：OpenClaw 常驻在你的机器上，性格、规则和记忆都是工作区里的文本文件，还会定时自己醒来。OpenHuman 接了一百多个应用，每一轮按 token 预算挑出相关的内容，并附上出处。ChatGPT Pulse 在夜里分析你的聊天记录和连上的邮箱、日历，早上给你几张卡片。

观点：它们把「上下文自己进来」做得很用力，这也是我最认同的方向。但组织方式多半还是一段对话或一叠卡片。一件要跑好几天、分成好几块的事，在对话里很难看清做到了哪。

### 监督面板

代表：[dsh-superagent](https://github.com/deepseek-ai/dsh-superagent-prototype)，DeepSeek 开源的研究原型。

{{fig:panel|监督面板：事情变成带授权的工单，人只看一块面板。}}

做法：事情从 GitHub 或飞书进来，经过把关和研判，变成一张带授权范围的工单，再派给一个执行会话。会话完全藏起来，人只看一块面板。它的原则写得很直白：尽量少占用人的注意力。

观点：这是和我想法最接近的一派，会话应该是实现细节。区别在服务对象：它服务的是一个团队和一个代码仓库，DS-buddy 服务的是一个人，和他手上的很多个项目。

### 这层抽象带来的误解和翻车

让 agent 互相传话，多数时候没有必要。人和人传话会走样，agent 也一样，还要多付一轮成本。

- **转述丢东西。**Cognition 在 2025 年 6 月的 [Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents) 里举过一个例子：做 Flappy Bird，把背景和小鸟分给两个子 agent，两边互相看不到，结果背景像马里奥，小鸟也不像 Flappy Bird。
- **转述还会多东西。**我自己翻过车：早先的版本里，我对助理说了一句目标，它转交给干活的 agent 时，顺手补了几条我没说过的要求，下游当成我的原话照着做了。现在交接只能引用我的原话，代码会核对那句话确实出自我。
- **agent 之间的话，被当成你的话。**助理越多，越容易出现假传授权。所以几家都在给消息标来源：Agent Teams 标注「来自另一个 Claude 会话」，Multica 区分「代表谁」和「凭谁的权限」。
- **抢同一件事。**没有一家只靠提示词来防重复：Agent Teams 用文件锁，Multica 用数据库按（issue，agent）串行化。
- **贵。**上面那个 15 倍的 token 用量，就是多开窗口的价钱。

2026 年 4 月 Cognition 又写了[一篇](https://cognition.com/blog/multi-agents-working)，结论收窄成一句话：多出来的 agent 可以贡献判断，写入要保持单线程。agent 之间任意互相通信的 swarm，他们的评价是大多在分散精力。

## fork 为什么多数时候更好用

fork 其实就是共享上下文，把已经知道的原样带过去。多 agent 之间靠转述，上下文在传递的过程里会丢。

这一点有源码可查。有一份对 8 个开源多 agent 项目源码的拆解（2026 年 7 月到 10 月的主分支，Claude Code 不开源，按官方文档），结论很一致：**没有哪个项目共享上下文窗口。**差别只在三件事上：子 agent 继承多少父历史，父 agent 写的任务说明长什么样，结果以什么形状回来。

{{fig:inherit|子 agent 启动时带着多少父对话。按源码行为定性摆放，同一个项目的两个位置代表两种模式。}}

去程，子 agent 看到什么：

| 项目 | 子 agent 看到什么 |
| --- | --- |
| Claude Code subagent（默认） | 自己的系统提示、环境信息、CLAUDE.md，加主 agent 写的一段委派消息。看不到父对话、已读文件 |
| Claude Code fork | 父的完整对话。用在「要全部背景、又不想污染主窗口」的时候 |
| Kimi CLI | 只有 prompt，加它自己的历史。系统提示里明说「主 agent 看不到你的上下文，只看得到你最后一条消息」 |
| Gemini CLI | 本地子 agent 只有任务说明，要求「必须带上用户的原始目标」；调远程 agent 只带 contextId 和 taskId |
| Codex | `spawn_agent` 只给任务；fork 时保留用户消息和最终答复，丢掉推理和工具往返 |
| OpenAI Agents SDK handoff | 默认整段对话历史，可以过滤，也可以先压成一段摘要再交过去 |
| LangGraph、AutoGen | 读写同一份 state，或者所有人共享一条消息线 |
| CrewAI | 只拿到上游任务的输出。它的提示里写着「对方对这件事一无所知」 |

回程，父 agent 拿到什么：

| 项目 | 父拿到什么 | 兜底 |
| --- | --- | --- |
| Gemini CLI | `complete_task` 的 JSON 报告，按 schema 校验 | 超时或超轮次给一次宽限轮，只许交结果 |
| Kimi CLI | 最后一条消息的文本 | 少于 200 字符自动追问一次 |
| Codex | 最终答复，经等待或完成通知回来 | 运行中可以续发消息、追加任务、打断 |
| Claude Code | 最终消息；后台任务以通知形式回来 | 可以续接，保留子 agent 自己的历史 |
| LangGraph Supervisor | 默认只留最后一条 | 可切到完整历史 |
| OpenAI Agents SDK handoff | 不回传，控制权直接转移 | 过滤或压缩历史 |
| AutoGen | 发言直接进入共享消息线 | 可换成有界的上下文 |

观点：默认的做法是只给一段说明，只收最后一条。任务说明写得怎么样，上下文就传得怎么样，几家的提示词都在要求父 agent「写全」。fork 是例外：Claude Code 和 Codex 都留了 fork 模式，用在需要全部背景的时候。Cognition 总结出来真正管用的几种做法里，也有一条是把完整上下文 fork 一份，去请教更强的模型。

## 但 fork 解决不了主对话变长

fork 不丢东西，也不减东西。它把全部背景带过去，代价是窗口一起步就很大，也贵。主对话还在一直变长，长到一定程度只能压缩，压缩是有损的，细节会丢。上下文太长，模型也会变糊涂。

回头看，多 agent 真正有用的地方在另一头：它给每件事单独开了一份干净的上下文。把名字和角色拿掉，剩下的就是一种管理 context 的办法。多 agent 这件事的本质，是给 AI 造一个管理 context 的好环境，围绕任务本身来组织上下文。

| 做法 | 每件事的上下文 | 里面的话 |
| --- | --- | --- |
| 多 agent | 干净，一件事一份 | 靠转述，会丢，也会多 |
| fork | 背着全部历史 | 原样 |
| 一开始就设计的上下文包 | 干净，一件事一份 | 你的原话逐字带进去 |

我想两头都要。所以我觉得，最好的上下文方案一定是一开始就有意识地设计出来的，靠对话一路聊下去是长不出来的。

## 一开始就设计：人说三件事，AI 来拆

往哪个方向搭？我觉得不该是让人来控制：组建频道，拉群，@ 谁。人只需要讲清楚三件事：要做什么，上下文在哪，标准是什么。

**要做什么。**在项目里说一句目标。这一次我说的是：下周四发布，做邀请函，再写媒体问答、口号和新闻稿，口号用中文还是英文，开工前先问我。它开了两个任务同时开工，口号那件没有开，先回来问我。

![项目对话：一句话交代发布会，开出两个任务，口号那件先问我](img/film-ask.jpg "一句话，两个任务，一个问题。")

**上下文在哪。**用 @ 指给它看：项目，文件，或者另一段对话。每个任务的产出都放在项目共享文件里，别的任务直接读，不用我转述。

![在输入框里打 @，可以选项目和项目里的文件](img/u2-at.jpg "两个任务刚交出来的文件，已经可以直接 @。")

**标准是什么。**每个任务有一栏「怎么算完成」。做完了交到我面前，只有我点了验收，这件事才算完。助理不能替我说「完成了」。

![交付面板：网页邀请函直接渲染，右上角是验收通过](img/film-accept.jpg "交回来的是成品，网页直接打开。")

然后由 AI 把它拆成一个个任务（thread），每个任务带一份上下文包。可以粗略理解成一份 goal 文件。

{{fig:pack|每个任务一份上下文包。它是长期维护的那一份；执行它的 runtime 是一次性的，开工时注入，有进展就写回。}}

任务详情，就是这份上下文包给人看的样子：

![任务详情：背景里附着我的原话，下面是怎么算完成](img/film-context.jpg "背景下面那一段是我的原话，再往下是怎么算完成。")

真正要长期维护的是它。落在产品里是这几条：

- **你的原话逐字带进去。**项目助理开任务时引用你那句话，服务端原样带给执行者，不经转述。助理补充的内容另外标出来，不算你的要求。
- **有进展就写回去。**交付、提问、失败都记在任务上。状态跟着事走，不跟着会话走。
- **只放用得上的。**大的材料放在项目共享文件里，只给路径。个人助理从时间线和记忆里带过来的资料，每条带出处，只作参考，不算你的要求。
- **确定的判断交给代码。**谁的话算授权，引文在不在原消息里，同一件事是不是提过两次，由代码核对。模型只做理解。

## agent 都是 tool，runtime 随时可以重来

至于那些临时干活的 agent，其实都是 tool。它们的状态很脆弱，也不太需要维护：就是一个 runtime，每次把上下文重新注入就好。

{{fig:tacit|DS-buddy 的结构：蓝色是上下文层。每件事 fork 一份去做，结果回到「待你决定」；你的每一下都记回去。}}

在 DS-buddy 里，任务默认由 DeepSeek Harness 里的一个会话执行，也可以在任务里换成 Claude Code 或 Codex。换的时候，新的执行者拿到的是任务上的那份记录，你看到的东西不变。同一件事会续接同一个会话，换一件事才开新的。

这里当然还有不少细节：每个 agent 启动时是不是一个全新的 context，怎么围绕缓存去省 token。别家在这上面下了不少功夫。Multica 把固定的说明放在前面，每次运行的信息追加在末尾。Raft 在一次线上读数里发现，2860 万提示 token 有 2710 万没命中缓存，之后改成每个会话冻结系统提示，变化只发增量通知。

我不确定 DS-buddy 现在的设计是不是最好的。但这些不该是用户感知得到的细节。

## 现在的产品暴露得太多了

同类的产品我看了不少，也学了不少。

Multica 和 Raft 都给出了一层很好的抽象。Multica 用工单：agent 在看板上领 issue，结果写在评论里。Raft 用群聊：agent 待在频道里，被 @ 到就去读，也会自己认领任务。这确实是好的组织方式，结果落在共享的记录上，人和别的 agent 都看得到。Claude Projects 走的是另一条路：一个项目里的几段对话共用一份资料和说明，没有 agent 这一层，但只能用 Claude 的模型，资料也主要靠人自己放进去。

这几样我都借鉴了：一件事有一份长期的记录，结果落在大家都看得到的地方，一个项目里的几段对话共用背景。

但还不够省事。在 Multica 和 Raft 里，agent 还摆在最前面：频道要人来建，issue 多半要人来开，谁做哪件也常常要人来点。对人来说，搭 context、做分工，本身就是一件费力的事，胶水的活只是换了个地方。理想的状态是 AI 自己把这一层做完。

| 架构 | 上下文怎么进来 | 按什么组织 | 人要管什么 | 怎么知道该你了 |
| --- | --- | --- | --- | --- |
| 角色团队 | 你来喂 | 看板或群聊 | 起名、配技能、盯进度 | 有的有收件箱 |
| 总指挥加分身 | 每次从头给 | 一次一个问题 | 分身看不见 | 只有最后的答案 |
| 并行比稿 | 每次从头给 | 一次一个问题 | 只挑模型 | 你来挑结果 |
| 常驻助理 | 消息、应用、文件 | 一段对话 | 有的要写规则文件 | 卡片或定时提醒 |
| 监督面板 | 代码仓库和群消息 | 工单 | 只有工单 | 面板 |
| DS-buddy | 屏幕、飞书、文件、你的话 | 项目和任务 | 没有名字，不用配 | 待你决定 |

这张表是按各家公开资料的读法，标的是一类做法，不是给某个产品打分。

## 最重要的设计：上下文的收集

AI 要自己做得了分工这一层，前提是摄入了足够多你的 context。在 Multica 和 Raft 里，一件事怎么拆、每件事带哪些背景，多半还是人来定。所以 DS-buddy 里最重要的一个设计，是上下文的收集。

![每 10 分钟，把原始记录整理成你在做的事](img/film-10min.jpg "时间线是这样来的：原始记录落到时间条上，每 10 分钟整理一次。示意动画。")

它是这样来的：

1. 屏幕上的应用、窗口标题和文字，每分钟读一次；飞书消息每 2 分钟读一次。全部只读，截图留在你的电脑上。
2. 每 10 分钟切成一窗，连同上一段在做什么、你有哪些项目，一起交给一次小模型调用。
3. 模型写出 0 到 3 件事，用你自己的任务说法；明显属于某个项目的，就归到那个项目。
4. 代码核对出处：每件事必须指回这一窗里的原始记录，指不回去的直接丢掉。

![时间线：一个上午的几段活动，各带用到的应用和所属项目](img/film-timeline.jpg "整理出来的时间线。每段带着用到的应用和所属的项目。")

两条边界：

- 观察到的信息是数据，不自动变成你的授权。屏幕和消息里出现的任何要求，都只当资料，不当指令。
- 不把所有东西不断拼进窗口。原始记录进存储，模型只取和这件事有关的那一段。

电脑里的文件走另一条路：你电脑上的一个小程序主动连过来，读哪些文件夹由你的电脑决定。

### 自动收集不是新鲜事

| 产品 | 怎么收集 | 收集来做什么 |
| --- | --- | --- |
| [Screenpipe](https://screenpipe.com/) | 在本地持续记录屏幕和声音 | 存成可以检索的历史，通过 MCP 给别的 AI 工具查 |
| [AirJelly](https://www.airjelly.ai/) | 读你允许的应用里当前窗口的内容 | 回看、问答，也能让 Codex 或 Claude Code 调取这份上下文 |
| [Littlebird](https://littlebird.ai/) | 通过辅助功能读当前窗口的文字，不录屏，也转写会议 | 攒成一份记忆，供它自己的助手使用 |
| Codex 的 Computer History | 通过辅助功能记下点击、输入、切换应用这些操作，不截屏，默认关闭 | 存成本地的记忆文件，给 ChatGPT 和 Codex 用 |

这张表按各家的公开资料和报道整理。读屏幕这一步，DS-buddy 用的就是 Screenpipe。

我看下来，它们多半停在记住和能查到：上下文存下来了，要用的时候由人或者 agent 去取。从看到的上下文里提出一件事，拆开，做完，再回到你面前等你拍板，这一圈还得人自己来接。

DS-buddy 想接上的是这一圈。时间线进了上下文层，个人助理随时能读，每一条都能核对出处。它把一件事交给项目时，带过去的是你的原话和相关的资料。别人在等你回的消息，会自动列进「待你决定」。夜里它把这一天过一遍，早上最多留三张卡。事情做完，回到的还是同一块看板。

## 你只管拍板

我觉得这会是以后的工作方式：人只在真正需要自己的地方开口，说喜好，说取舍，给出关键的那一下指引，不再当信息的搬运工。

事情并行跑起来，最难的是看不过来。「待你决定」是一块跨项目的看板，分三栏：等你，进行中，今天完成。等你那一栏放的是需要你的：等你拍板的，等你验收的，出了错的，还有别人在等你回的消息。

![待你决定：点一下提醒卡，回复写进输入框](img/film-board.jpg "有人在群里等你回复，它先记下。点一下，回复就写好。")

- 卡片上没有按钮。点任务卡打开任务；点提醒卡，一句话写进输入框，你改完再发。
- 个人助理不进项目干活，它跨任务看。夜里电脑空闲时把这一天过一遍，早上最多留三张卡：一件可以做的，一样值得看的，一句想说的，每张写明出处。
- 做完没有，和它还在不在跑，是两件事。排队不能冒充正在执行，一个回合结束也不等于这件事解决了。只有你点了验收才算完成。

## Tacit：默会

里面那个助理，默认的名字叫 Tacit，取的是「默会」的意思，心领神会。我觉得一个真正好的 buddy，应该在你开口之前，就已经了解和这件事有关的一切。到那时候，背后有几个 agent、各叫什么，你不需要知道。

![左边对话里说记住，右边记忆页关于你这一条带原话](img/u6-memory.jpg "左边是我说的话，右边是记忆页里的这一条，下面附着原话。")

- 「关于你」只记你亲口说过的话，每条附着原话，代码核对确实出自你。记得不准就改，不想要的直接忘掉。
- 技能不用你配。同一个问题你在交付后说了三次，夜里它起草一版新的「做事说明」，只改怎么做，不加权限；早上由你选用新版、先试一次，还是保持旧版。
- 它不以你的名义行事。没有你的一句话，不拍板、不验收，也不替你发消息。飞书和电脑文件夹都是只读，而且只读你允许的。

## 还没做好的

- 反馈现在主要还靠人。哪些环节能交给自动检查，我还在试。
- 时间线的整理不总是对。相邻几段容易被前一段带偏，写成同一件事；原始记录还在，但要靠你发现。
- 任务是 AI 拆的，项目现在还得你来建，或者说一句让它建。
- 换执行者只在一轮做完之后生效，跑到一半怎么交接还没有好答案。Codex 当执行者，还没有验证到它跑完一个完整任务。
- 每个 agent 启动时的上下文怎么组织、缓存怎么用，我不确定现在是不是最好的。
- 上下文越多越要防污染。给每条信息标来源是第一步，够不够要看更多真实使用。

## 开始用

DS-buddy 是 DeepSeek Harness 的一个开源插件，需要 DeepSeek Harness 0.2.x 和 Node 24。装好后左侧会多出「个人助理」和「项目」，模型跟着你的 DeepSeek Harness 配置走。新建一个项目，说第一句目标就行。读屏幕和电脑文件需要在你的 Mac 上另装一个小程序，不装也能用项目和任务。

代码在 [github.com/DKKD13/tacit-dsh](https://github.com/DKKD13/tacit-dsh)。
